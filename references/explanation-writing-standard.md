# Sourceに合わせる問題解説

正答・誤答解説を作成・修正・レビューするときに使う。[source-calibrated-question-writing.md](source-calibrated-question-writing.md) のSource優先順位を共有する。資料の照合、全候補の理由の分析、説明方法の分布と採用方針は [source-analysis-method.md](source-analysis-method.md) に従う。解説が補った前提とStemの条件、Sourceが述べる理由と一次情報で確認できた事実を分ける。

## 1. 既定方針と上書き

既定は、候補ごとの動作と問題の条件を結び、正しい／外れる理由を必要な詳しさで説明する共通原則とする。今回の解説資料があれば、確認できた構成、説明順、語調、段落、詳しさを優先する。未観察部分は以下の原則で補い、別資格の説明形式を引き継がない。

- 選択肢を一つずつ取り上げ、正しい／誤りの理由を短い段落で直接説明する。全問共通の長い導入、決定要因の章、まとめは前提にしていない。
- 機能・動作を説明して条件へ接続する。できない操作、誤った対象、異なる上限が論点なら、その違いを直接指摘してよい。
- 実行可能でも費用・開発・管理が増える候補を、機能的に実行できない候補と区別する。比較に不要な機能説明は足さない。
- 説明量は論点によって変わる。単一の誤認は短く、複数Serviceの連携は接続を追えるだけ説明する。
- 正答・誤答の両方に理由を示す。資料中の回答履歴や重複した参照案内、説明の言い直しまで模倣しない。

製品仕様は一次情報で確認し、資料の誤記、断片、古い制限を受け継がない。原則の検討に使った過去の観察は [問題文基準の観察例](source-calibrated-question-writing.md#8-原則の検討に使った観察例) に残すが、対象資格の出題根拠としては使わない。

## 2. 必要な理由を、必要な長さで書く

正答または正答集合を明示し、各候補が今回正しい／外れる具体的な理由を読めるようにする。次は説明に使える観点であり、すべての候補に別々の文やFieldを必須にするものではない。

- 候補は何をするか、何ができないか。
- 問題のどの条件がその違いを重要にするか。
- 採用すると何が満たされ、どこで失敗し、何の追加作業が生じるか。

候補の機能を知らないと理由が伝わらない場合は、まず役割を平易に説明する。誤った設定値や対象の違いが論点なら、その誤りから始めてよい。条件との因果が一文で閉じるなら一文でよく、４要素・４文・2〜4文・一定文字数へ揃えない。共通前提を問全体で一度説明し、各候補で差分だけを述べてもよい。

正答は何が要求を満たすかを示す。誤答は「要件を満たさない」だけにせず、できない操作、足りない権限、余分な管理作業、違う処理対象など、今回の理由を特定する。「別の状況では有効」という説明は比較に役立つ場合だけ付け、実在しない機能や誤構文へ無理に長所を作らない。

運用負荷の削減を求める問題なら、Instance選択、Cluster管理、移行、独自Code、Data加工など、どの作業が増減するかまで比べる。費用効率なら費用の発生箇所、Latencyなら処理経路や待ち時間を説明する。評価軸は本文の意味から読み、「運用負荷が高い」「遅い」だけで結論にしない。

複数候補が必須要件を満たす問題では、正答が指定評価軸で優れる理由を説明する。誤答には、実行不可能なのか、必須条件に違反するのか、実現可能だが比較で劣るのかを正確に反映する。実現可能な候補を「このServiceではできない」と誤説明しない。費用と運用作業を取り違えず、問題文にない事情で優劣を後付けしない。

Sourceに全体Summaryがなければ追加を既定にしない。判断ルール、用語補足、関連Linkは理解に役立つときに置き、候補別解説を言い直すだけなら省く。内部のFamily、Case ID、`decision_rule`、`contract`、`boundary`といった分類語を、その対象を説明せず本文へ流さない。

## 3. 問題形式に合う説明にする

### Single Choice

一つの正答と全誤答の理由を説明する。解説の長さを揃える必要はないが、誤答だけが抽象的・省略的にならないようにする。解答前の選択肢の長さや文体による手掛かりは別途検査する。

### Multiple Response

問いが要求する関係を先に判別する。

- **独立に正しいものを複数選ぶ**: 対象となる操作、原因、解決策等を各候補で判定する。例えば「このErrorを解決できる方法を２つ」なら、各方法が単独で解決できる場合がある。同時実施や順序を捏造しない。
- **組み合わせて要求を満たす**: 各正答の役割、接続、組合せ全体が満たす条件を説明する。抜けると失敗する役割や不要な候補は、その関係を理解するのに必要な分だけ示す。全組合せを列挙しない。

どちらも正答集合が問題の選択条件を満たし、各候補の採否を説明できることを品質下限にする。「必要十分」を全形式に一律の協調動作として解釈しない。

### Ordering／Matching

Orderingは前後の依存関係と不要な手順を説明する。番号列の復唱だけで終えず、無関係な順序まで必然としない。Matchingは各対象と候補を結ぶ理由と紛らわしい対応を示し、候補の再利用可否を守る。新しいSourceで未観察の形式は、未観察と記録してこの機能上の基準で補う。

### Artifact

Code、設定、Data、Logなどでは、候補内の具体的な差と実際の検証結果を説明する。全Optionの `artifact_selection.explanation_bindings`、共通Fixture等の結果、正答集合は一致させる。自然文へ直してもこのEvidence契約を外さない。詳細は [exam-question-fidelity.md](exam-question-fidelity.md) に従う。

## 4. 生成元とレビュー

正規Sourceには候補別に完成した自然な解説を保持する。必要なら機能・決定条件・不適合・結果をレビュー用情報として持てるが、`candidate_capability`、`decisive_constraint`、`fit_or_mismatch`、`consequence`の固定連結で全解説を作らない。既存Schemaにこれらがある場合も、情報の重複を整理して自然文を別に保持できるようにする。

Source profileには採用した説明の特徴と異なる完全例の所在を記録する。GeneratorがProfileを参照するだけで固定Templateを使い続けていないか、完成例と最終出力の両方を読む。文・段落・共通接頭辞／末尾の反復は、Bank、形式、生成Familyを横断して検査する。

次を不合格にする。

- 全候補の理由が正誤ラベル、一般論、選択肢の復唱だけ。
- 固有名詞を交換しても別の問題へそのまま貼れる因果説明。
- 個別理由の前後へ同じ長い導入・結論を追加して説明量を稼ぐ。
- 独立した複数の解決策を、同時実行必須の手順と誤解説する。
- 候補にない動作、Sourceの誤記、検証結果と違う理由、未説明語の連鎖。

短い接続語、正誤ラベル、同じAPI名の反復だけを失敗にしない。共通する技術的事実の短い再説明は必要な場合に認める。機械的な文字数・類似度の警告は読み直す起点であり、Paddingや同義語置換で解消しない。自然に読めることと候補固有の理由があることを、全件の意味レビューで確認する。
