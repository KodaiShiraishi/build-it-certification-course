# ADRとSkill改善ループ

この手順は、このSkillを使うすべてのプロジェクト作業で適用する。目的は、プロジェクト固有の意思決定をADRに残し、実証済みで汎用的な知見だけをSkillへ還元することにある。

## 1. ADRの配置を決める

1. 実際に変更、設計、監査する成果物を含むプロジェクトルートを特定する。単一の子リポジトリが対象なら、集合ディレクトリではなくそのリポジトリを選ぶ。
2. `docs/adr/`、`docs/architecture/decisions/`、`adr/`、既存ADRへの参照を検索し、既存の配置、番号、テンプレート、文体を優先する。
3. 規約がなければ `<project-root>/docs/adr/YYYYMMDD-short-title.md` を使う。同じ判断を継続する場合は同じADRを更新し、別の判断と衝突する場合だけ短い接尾辞を付ける。
4. 複数リポジトリへ一つの判断を適用する場合は、主対象のプロジェクトに一つ作り、対象リポジトリを列挙する。独立した判断が必要なら各プロジェクトに分ける。

書き込み可能なプロジェクトが存在しない場合だけ、最終回答にADR案を示して未保存と明記する。保存していないADRを作成済みとして扱わない。

## 2. 作業中にADRを更新する

空の雛形だけを先に置かず、判断の背景を説明できる時点で、最初の教材・コード変更より前にADRを作る。最低限、次を含める。

```markdown
# ADR: <判断の題名>

- Status: Proposed | Accepted | Superseded
- Date: YYYY-MM-DD

## Context
## Decision
## Rationale
## Alternatives considered
## Consequences
## Scope
## Verification
## Skill feedback
```

- 相談・構成案では `Proposed`、実装して検証した判断では `Accepted` を基本とする。
- 監査・レビューだけの依頼でもADRは作成または更新するが、ADR以外のプロジェクトファイルは変更しない。
- 事実の羅列ではなく、採用した判断、理由、退けた代替案、受け入れる不利益を記録する。
- 公式仕様に依存する判断には、出典、確認日、対象バージョンを記録する。
- 完了前に実際の差分と検証結果へ合わせ、予定のまま残さない。
- 公開後にCommitやCI／Deploy runをADRへ追記する場合は、学習者向け変更を実際に含むReleaseとその検証Evidenceを記録する。その記録だけの追跡Commitがもう一度CIを起動したときは最終報告で新しいHEADとRunを示し、先行する記録Commitだけが起動したRunを記すためにADRを再更新し続けない。内容変更を伴うRunはこの停止条件の対象外とし、通常どおりADRと検証を更新する。
- 既存ADRを黙って上書きしない。判断が変わった場合は `Superseded` と後継ADRの関係を残す。

## 3. 汎用性を判定する

完了前に、作業中の失敗、手戻り、レビュー指摘、検証結果、成功した手順を既存Skillと比較する。次をすべて満たす改善をSkillへ反映する。

1. 複数の資格、ベンダー、または別構成のリポジトリでも繰り返し役立つ。
2. 今回の実作業、再現可能な検査、または信頼できる一次情報で有効性を確認できた。
3. 既存のSkillだけでは同じ失敗や判断漏れが再発し得る。
4. 秘密情報、個別URL、ローカル専用パス、単一プロジェクトの命名へ依存しない。
5. 短期的に変わる試験範囲や製品仕様そのものではなく、確認方法や判断手順として一般化できる。

一つでも満たさない知見は、ADR、公式情報の対応表、またはプロジェクト固有の検証へ留める。「念のため」だけでSkillを肥大化させない。

## 4. 適切な生成元を更新する

- ほぼすべての利用で必要な契約・順序・境界は `SKILL.md` に置く。
- 特定の作業でだけ必要な詳しい手順や基準は `references/` に置き、`SKILL.md` から直接リンクする。
- 繰り返す機械検査や生成処理は `scripts/` に置き、代表ケースと失敗ケースで実行確認する。
- Skillの適用条件やUI上の約束が変わった場合だけ `agents/openai.yaml` を再生成する。

更新は既存の指示と重複させず、問題を再発させない最小差分にする。適用範囲の拡大、既存方針との衝突、外部サービスの追加、大きな互換性変更が必要ならユーザーへ確認する。

## 5. 検証してADRへ戻す

Skillを更新した場合は、少なくとも次を行う。

1. `skill-creator/scripts/quick_validate.py <skill-folder>` を実行する。日本語を含むSkillをWindowsで検証する場合はPythonのUTF-8モードを有効にする。この検証スクリプトにはPyYAMLが必要なため、既にPyYAMLを利用できるPython環境を選び、検証だけのために無断で依存を追加しない。
2. 追加・変更した参照ファイルが `SKILL.md` から到達できることを確認する。
3. スクリプトを変更した場合は代表的な成功ケースと失敗ケースを実行する。
4. UIメタデータを変えた場合は `agents/openai.yaml` を再生成し、Skill本文との整合を確認する。
5. ADRの `Skill feedback` に、更新したファイルと検証結果を記録する。更新しなかった場合は、その理由を記録する。

Skill更新そのもののために別のADRを連鎖的に作らない。現在のプロジェクトADRを、この作業の判断とSkillへの還元を結ぶ記録として使う。
