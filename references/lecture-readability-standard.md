# IT資格講義の読みやすさ基準

講義の新規制作、説明不足の改善、用語集追加、初心者導線の整備で使う。

## 1. 前提知識を可視化する

各章で必要な前提を列挙し、次の三つに分ける。

- 対象読者が既に知っていると確認できたもの
- 本講義より前に説明するもの
- 任意の基礎ページまたは用語集で補うもの

「エンジニアなら知っているはず」「資格受験者なら当然」と推測して省略しない。高度な主講義と、初学者が追いつくための基礎導線を分ければ、経験者を退屈させずに前提不足も防げる。

## 2. 説明の順序

重要概念では、次の順序を基本にする。

1. 選択された教材言語による平易な一文要約
2. 解決したい具体的な困りごと
3. 小さなデータ、システム、運用場面の例
4. 正式な用語と構成要素
5. 入力から出力までの処理順
6. その動作になる理由
7. 設定しない場合、壊れた場合の症状
8. 代替案と判断基準
9. 試験問題で注目する語句と切り分け方

定義を先に置くことで理解しにくくなる場合、例から定義へ進める。比喩は入口として使い、比喩と実際の技術がどこで異なるかも示す。

## 3. 専門用語の扱い

- 用語を最初に使う場所で、短く意味を説明する。
- 定義文に未説明語が二つ以上現れる場合、さらに基礎へ分解する。
- 略語は正式名称だけで終わらせず、何をするものかを書く。
- 専門用語を別言語の音写や未説明な借用語へ置き換えただけのものを、選択された教材言語での説明とみなさない。
- 一つの語に複数の意味がある場合、製品、実行単位、保存単位などの軸を明記する。
- 製品名が変わった場合、現行名、旧名、試験や画面で見える名前を整理する。

## 4. 初心者向け導入ページ

IT資格講義では、必要に応じて次を一つの短い流れで説明する。

- データ、ファイル、ディレクトリ、表、行、列、キー
- プログラム、コード、SQL、クエリ、API、UI
- サーバー、CPU、メモリ、ディスク、ネットワーク
- ストレージとコンピュートの違い
- スキーマ、メタデータ、ログ、メトリクス
- バッチ、ストリーミング、ジョブ、タスク、パイプライン
- 権限、認証、認可、監査

すべてを辞書のように並べず、例えば「ファイルを受け取り、処理し、表へ保存し、監視する」のような一つの処理を追わせる。

## 5. クリック可能な用語集

- 人間が読める安定した固定アンカーを使う。自動生成見出しだけに依存しない。
- 講義の初出、比較表、演習、問題解説から同じアンカーへリンクする。
- 各項目を「一言でいうと → 具体例 → 似た語との違い → 関連講義」の順で書く。
- アンカー重複、リンク切れ、大文字小文字、URLエンコードをビルド後HTMLでも検査する。
- 用語集だけを読ませず、本文内にも最小限の説明を残す。

## 6. ページ単位の最低基準

講座全体では、上部Navigationに確定した教材言語の独立したServiceカテゴリを置き、Domain／Task講義と問題より前から見えるようにする。そこから各固有Service／主要機能の包括的講義へ直接移動できるようにし、Serviceを体系的に学びたい読者が設計講義を探し回らない構造にする。責務Familyでページをまとめてもよいが、Landingから各正式名称の固定Anchorへ直接移動できなければならない。

主要ページに次があるか確認する。

- [ ] 一文要約
- [ ] 具体例または小さなシナリオ
- [ ] 必要な理由
- [ ] 誤解した場合に起きること
- [ ] 前提語へのリンク
- [ ] 処理順または責務の境界
- [ ] 比較・トレードオフ
- [ ] 試験または実務での判断ポイント
- [ ] 確定した教材言語のServiceセクションがあり、その講義で使う製品Serviceまたは主要機能を名前の列挙ではなく仕組みから説明している

囲み、表、箇条書きが存在するだけでは合格にしない。本文を順に読んで、未説明語なしに因果関係を再現できるかを判定する。

Serviceセクションは別冊handbookへのリンクや「この講義で使うService」の一覧だけで済ませない。設計判断へ進む前に、その講義で使う各Serviceの役割、内部処理、設定、Security、障害、観測、Cost／Performance、代替、連携、具体例を本文として教える。講義をまたいで同じServiceを再利用する場合も、現在のScenarioで必要なMechanismと責務境界を現在の講義内で再構成し、既知であることを暗黙に仮定しない。

上部Service curriculumと本文内Serviceセクションは役割を分ける。上部CurriculumではService自体を入口から体系的に教え、本文内セクションでは現在のScenarioへ適用する。どちらか一方へのLinkだけで他方の説明を省略せず、初学者は上部から順に、経験者は必要なServiceまたはDomain講義へ直接移動できるようにする。

上部Curriculumの固有Service Entryは、用語集のように `Service名 → 一言でいうと何か` から始める。ただし用語集の短い定義で終えず、解決する問題、構成要素と処理順、設定とSecurity、障害時の症状と観測、Cost／Performance、代替、Integration、具体的な設計例まで同じEntry内で説明する。Familyの導入文を読まないと意味が成立する書き方や、名前一覧の後にFamily共通の11見出しを置く構成を合格にしない。

生成またはTemplate展開する講義では、Rendererだけでなく正規SourceのSchemaを確認する。少なくとも概念固有の定義、前提、仕組み、具体的Scenario、処理順、障害Evidence、比較条件を表現できること。Sourceが名前、推奨Control、誤答候補だけなら、長い共通Templateで補わずSchemaから直す。

同じ見出しがあることや最低語数を満たすことを、説明の深さとして数えない。各概念に固有のMechanism、Evidence、Decision boundaryが本文として存在し、読者がScenarioから判断までを再現できることを確認する。

## 7. 領域間の深さ

- ページ数、本文量、例の数、演習数、通常問題数を領域ごとに比較する。
- 得意領域や作りやすい領域だけが厚くなっていないか確認する。
- ユーザーが「この領域はもう十分」と指定したら、その領域を増やさず、薄い領域を優先する。
- 短いページを水増しするのではなく、目的、内部動作、障害、比較、実例の不足を埋める。

## 8. 読みやすさの検証

- 用語の使用順を検索し、定義より先に使われていないか確認する。
- 対象ページ全数について、導入、理由、具体例、用語リンクの有無を検査する。
- 生成講義群では、正規化した完全一致の文・段落と共通語数をページ横断で集計する。見出し、Navigation、共通Safety注意などを教育本文と分け、共通定型文の分子・分母・上限を記録する。固定の全資格共通閾値は設けず、Corpus規模と教材形式に合う上限をプロジェクト側で定める。
- 講義Scenario、用語集の具体例、障害診断が、名称やTask IDだけを差し替えた同一文になっていないことを正規化重複で検査する。語数を増やすだけの共通接頭辞・末尾・Paddingを固有説明へ数えない。
- 見出しと語数は揃っているが、定義、仕組み、Evidence、Decision boundaryが汎用文だけのNegative fixtureを用意し、深さGateがFailすることを確認する。
- 二つの固有Service Entryから正式名称を除去すると本文が同一になるNegative fixture、Family総論しかないFixture、一文定義だけのFixture、Landingから固定Anchorへ直接移動できないFixtureをFailさせる。
- 生成HTMLでアンカー、内部リンク、目次、前後移動を検査する。
- PC幅とスマートフォン幅で、表、コード、数式、図が読めるか確認する。
- 独立レビューでは、技術的に正しいかだけでなく、前提不足と説明の飛躍を指摘させる。
