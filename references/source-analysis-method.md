# 問題・解説Sourceを分析し、制作配分へつなぐ

問題Sourceの分析から講座を制作・全面再作成するとき、または「どんな問題が何割あるか」を調べるときに使う。**学習者に何を判断させ、その答えを何が決めるか**を、問題文・全候補・解説の意味から分析する基準。AWS、Microsoft、Google等の試験提供元や教材言語に依存しない。AWS AIP資料分析から得た方法を一般化しており、固有の語句、出題形式、件数・比率・Service構成を既定値にしない。

集計・注釈は既存の `question_source_profile`／`explanation_source_profile` や同等の記録へ統合する。この文書は新たな必須JSON Schema、全問の定型文、固定のレビュー回数を追加しない。公式Scope・Artifactの算入・既存Schemaは [exam-question-fidelity.md](exam-question-fidelity.md)、執筆は [問題文の基準](source-calibrated-question-writing.md) と [解説の基準](explanation-writing-standard.md) に従う。

## 1. 集計単位と根拠を先に決める

- 資料ごとに役割、版・確認日、Hash、問題セットの境界、完全問、断片、重複、欠落を確認する。番号、見出し、画面上の「全75問」等を、そのまま入手済み問数にしない。
- 問題と解説をStem・候補で照合し、出典位置へ戻れるIDを付ける。同じ問題の解説、選択肢の並べ替え、再掲、翻訳を独立の出題数として加算しない。似た判断の別問は別に保持し、同じ内容Familyへの偏りとしても見る。
- 共通Scenarioに複数の設問がある場合は、各設問を分析単位とし、参照する共通条件を含めて読む。Scenario数と設問数、同じ設問内の候補数を混ぜない。
- 解説資料にしかない完全な独自問題は、問題部分を一意問として分析対象にできる。その場合も、解説の件数を足すのではなく、問題本文の存在、重複の有無、出所を確認する。対応しない解説断片は問題形式・出題頻度の母数へ入れない。
- 元資料別の集計を残してから統合する。統合は一意問を等重みとするのか、セットごとの重みを調整するのかを明示する。同じ問を複数資料で二重計上せず、少数の解説例や特定分野の資料が全体を代表すると仮定しない。
- 各割合に分子・分母・対象集合・未分類数を付ける。問題単位、選択肢単位、解説単位の割合を混ぜない。分類軸ごとに完全性が違う断片は、判定可能な項目だけ使い、その軸の母数を明記する。

全体の意味分類比率を制作根拠にするなら、対象の全問についてStemと全候補を読み、必要に応じ解説を確認して、問ごとの分類と根拠箇所を残す。標本分析なら、抽出方法、対象範囲、実読数、未読・不明範囲を示し、標本の比率として報告する。検索は出典箇所の探索に使えるが、特定単語の有無を分類条件、分析対象の絞り込み、意味分類の件数に使わない。集計は本文の読解に基づく注釈から行う。

## 2. 一つの「問題タイプ」へ混ぜず、軸を分ける

まず各問について「答える対象」「守る条件」「候補・回答を区別する理由」を自分の言葉で短く整理する。そのうえで異なる代表例から分類を組み立て、包含・除外条件と曖昧な場合の扱いを記録する。下表は分析の観点であり、全資格に同じ分類名・種類数を強制するものではない。言い回し・翻訳・製品名だけが違っても同じ判断構造は同じ分類にし、同じ問い方でも判断根拠が違えば分ける。

| 分析軸 | 観察するもの | 混同しないもの |
|---|---|---|
| 解答形式 | 単一選択、複数選択、並べ替え、対応付け、自由回答。候補数と指定選択数を別々に記録 | 四択かどうかと、問われる判断の難しさ |
| 主な正答決定の根拠 | 要件充足、評価軸による最適化、原因診断、機能・知識の識別、計算、依存関係など | 特定の単語・問い方と、答えを決める論理 |
| 回答対象・作業の形 | Architecture／Service選択、設定・API選択、手順・Lifecycle設計、調査・修復、評価・監視設計、Code・Data解釈など | 「設定を選ぶ問題」は必ず機能暗記、という扱い |
| 思考の特徴と難易度 | 知識再生・適用・統合、必要な前提、推論段階、候補の近さ。難易度の見積り理由 | 思考の種類をそのまま難易度と呼ぶこと、推定難易度と実測正答率 |
| 最適化の軸 | 運用保守、初期実装、費用、Latency、Throughput、信頼性等。方向と優先順位も記録 | 費用と保守作業、初期移行と定常運用、LatencyとThroughput |
| 候補・正答の関係 | 独立した完全案、単独で正しい複数案、組合せで成立する要素、依存順、対応関係 | 複数選択の全候補を一つの共同実行案にすること |
| 問う内容 | 主Objective・主内容Family、Service／Feature、連携、Lifecycle、読者に必要な前提知識 | 製品名の登場回数と、その製品の理解が正答を決める問数 |
| Scenarioと制約 | 既存構成、変更目的、入力・出力、権限、更新・障害、期限、規模、互換性、Region／版／実行方式 | 背景の言及と、必須条件・比較を決める条件 |
| 誤答がもっともらしい理由 | 近接機能、適用範囲、対象・粒度、順序、未完成の連携、要件違反、実現可能だが劣る案 | 誤答をすべて「実行できない」とすること |
| 判断に使う実物 | Stem／OptionにあるCode・設定・表・Log・図、その行・値・関係を読む必要性 | 「JSON」「ログ」という語の登場だけでArtifactと数えること |
| 文章の構成 | 状況→要求→問いの流れ、長短の幅、制約密度、候補の粒度、用語導入、肯定／否定の問い方 | 長文や専門語の多さを難易度とすること |

主分類は原則一問一つとし、競合する場合は決定を支配する根拠を選び、補助Labelと理由を残す。判定できないものは `unresolved`／`unmapped` 等で残す。Service、制約、最適化軸のような複数Labelは重複可とし、合計が100%を超え得ることを示す。

不明・未解決は分類軸ごとに記録する。問いが費用比較を求めると分かる一方、負荷条件がなく正答を確定できないなら、主な判断根拠は費用最適化、比較の妥当性は条件不足とする。正答未確定という状態を、原因診断・要件充足・最適化と同じ主分類の別区分へ置かない。判断の種類自体を読み取れない場合だけ、その軸を未分類とする。

たとえば「設定を選ぶ」は回答対象であり、その正答根拠は「唯一互換性がある」場合も、「三案とも互換性があるが保守作業が少ない」場合もある。主な判断根拠と回答対象を別々に数えることで、この差を制作へ反映できる。

## 3. 正答を決める比較の構造を読む

最適化は正答を決める構造の一つとして扱う。全問について、要件違反の排除、成立案同士の優劣、原因と観測の対応、操作の依存順、役割の組合せ等、実際に求められる判断を読む。「比較問題」を報告するときは、どの構造を含めたかを定義し、候補が複数あるだけで最適化比較としない。

優劣の判断は、問いの末尾だけでなく、共通Scenario、業務上の目的、制約の優先順位と全候補の関係から確認する。例えば「管理担当者を増員できないため、定例の手作業を減らすことを優先する。構成を提案せよ」は最上級の単語がなくても運用上の優劣を求める。一方「最も考えられる原因を選べ」は原因診断であり、性能・費用等の最適化ではない。同じ費用の記述でも「月額上限内」は適合条件、「他条件を満たす中で支出を抑える」は優劣の軸となる。いずれも特定語句の対応表で判定しない。

最適化を求めると読めた問では、次の二段階を記録する。単語のない問を除外せず、本文にない優先順位も補わない。

1. **問いの意図**: 評価軸を指定する箇所、最小化／最大化の方向、比較の対象。複数軸なら同順位、主従、上限制約との関係。
2. **実際の判断構造**: 比較単位ごとに必須要件を満たすか、実現可能な不採用案があるか、指定軸で正答を選ぶ具体的根拠があるか。

比較単位が単独候補か組合せかを先に確定し、次の違いを記録する。排他的な内訳にする場合は条件不足・欠落等が重なる際の判定順を定義する。補完型という候補関係は、組合せ間の比較が成立するかと別軸であり、同じ問を二つの排他区分へ数えない。

| 観察結果 | 記録上の扱い |
|---|---|
| 複数案が要件を満たし、指定軸で採否を説明できる | 成立が確認できた最適化比較 |
| 複数案は成立するが、比較根拠が不足し同点・優劣不明 | 複数実現可能・順位未確定 |
| Region、実行方式、未提示の負荷や料金等で可否・順位が変わる | 条件付き・根拠不足。足りない条件を特定 |
| 要件を満たす完全案が一つしかない | 最適化を求める意図はあるが、観察された選別は要件充足 |
| 複数の正答が一つの構成を補完するだけ | 補完関係。別の実現可能な組合せとの比較があるかをさらに調べる |
| 問題・解説の欠落や矛盾で判定できない | 未解決として保持し、成立済みへ繰り入れない |

この区別から、「最適化を求める問の割合」と「実現可能な不採用案まで確認できた比較問の割合」を別々に出せる。解説で初めて補われた条件は、その出所も記録する。Sourceの曖昧さや技術的な誤りを、新しい問題へ再現しない。

比較の構成も必要に応じて定義して数える。例はManaged同士、独自処理との比較、共通部品を残して一工程だけを変える比較、既存基盤の再利用。自由記述Tagの欠落を「その構成はない」と扱わず、同じ定義で候補を読み直す。これらの構成や比率を全資格へ一律に課さない。

### 正解を決める条件を読む

「既存基盤がある」は、それだけで再利用必須や最小保守を意味しない。指定機能が対応済みで、必要な権限・性能・入力条件を満たし、比較対象より何の追加作業を減らすかまで読む。「ログとData sourceを関連付ける」なら、どのID・版・時点を結び、どの証拠を追跡するのかを確認する。単なる製品名の共起を連携判断として数えない。

実現可能性は目的のAPIを呼べるだけでは足りない。問題が要求する範囲で、受付と完了、取得漏れ・Pagination、再試行と重複、障害復旧、権限、Dataや結果の到達先まで含む完全な案かを確認する。逆に、その問題に要求されない完全監査や厳しい締切を勝手に追加して、成立する案を排除しない。

候補がArchitecture全体、Service固有機能、設定、個別操作のどの粒度を提案しているかを保つ。「レビュー工程を設ける」という構成案を、そのServiceに自動レビュー機能があるという主張へ読み替えない。候補どおりで成立する案、局所修正で成立する案、必須機構が欠ける案、情報不足の案を分け、修正すれば成立することを元の候補の成立証拠にしない。

全実現可能案に共通する「同じ性能・品質試験を通過済み」という条件は、本文で一度示せる。採否や順位を変えない共通前提を、各候補のMetadataへ逐語的に重複させること自体を品質条件にしない。特定案だけの適合に必要な前提、正答を変える制約、候補間の比較根拠は省略しない。一つの要件違反を、別の要件にも違反する証拠として流用しない。

運用負荷は、所有するCode、状態管理、配置、更新、監視、復旧等の差へ分解する。費用は同じWorkload・期間・必要機能での構成全体を比較し、共通費用と追加費用を分ける。複数軸では、一案が両方で優れるのか、Trade-offの解消規則が必要なのかを区別する。根拠のない換算や「Managedだから」で同点を解消しない。

### 複数選択では組合せの単位を保つ

- 単独で正しい方法をN個選ぶなら、それぞれが単独で要求を満たすかを判定する。上位N案を選ぶ問題では採用群と不採用群の境界を調べ、不要な採用群内の順位を捏造しない。
- 要素を組み合わせるなら、各要素の役割と、選択数に従う組合せ全体の充足・不足を調べる。三要素の各々が良さそうでも、同じ役割を重複し別の役割を欠けば成立しない。
- 組合せの最適化では、実現可能な別の組合せとの保守・費用等の差を確認する。少数候補なら全組合せ、規模が大きければ役割・依存関係による同等の網羅的検証を使う。学習者向け解説へ全組合せ表を強制しない。

## 4. 解説Sourceからは「判断を説明する方法」を抽出する

Stem・全候補との対応を確認してから、正答・誤答別に、何が説明され、どこが省略され、どの程度の前提知識を求めるかを読む。全候補分の理由の有無と実読範囲を残す。問題のTopic頻度と、解説で詳しく扱われるTopic頻度は別に集計する。

- 候補の役割・機能から始めるか、誤った対象・設定を直接指摘するか。短い誤認と複雑な連携で説明量がどう変わるか。
- 問題のどの条件を根拠に、適合・不適合・優劣を説明するか。候補の復唱で終わらず、動作→条件との関係→結果の因果が読めるか。
- 実行不可能、要件違反、実現可能だが比較で劣る、補完する役割、を説明上も分けているか。
- 不採用案が有効になる別条件、選択を変える境界、注意点を、実際にどの場面で補足しているか。全候補へ「別の状況では有効」を機械的に追加しない。
- 問題文にない前提、古い仕様、一次情報と矛盾する理由を解説が補っていないか。書き方として採用する特徴と、技術内容の採否を分ける。
- 用語の初出説明、具体例、参照Link、全体Summary、選択肢ごとの長さの幅を観察する。欠けた末尾やUIの再掲を文体の特徴としない。

説明方法の分布を使う場合は、機能説明、要件との接続、実現可能な劣後案、依存関係等を候補ごとの理由へ重複可で分類し、正答理由と誤答理由も必要に応じて分ける。理由がない候補と未読の候補を、説明方法がない観察済み例に数えない。資料別に「観察した箇所・特徴」「採用する執筆方針」「除外・不明点」を対応づけ、同じ文章構造や文数の固定Templateへ変換しない。

## 5. 件数・割合・組合せを示す

最低限、解答形式、主な正答決定の根拠、回答対象、最適化軸、実現可能案の比較構造について、対象Sourceの件数と割合を確認する。Topic・内容Family、誤答の種類、Artifact、文章長等は制作判断に役立つ内訳を加える。

- 一意の主分類は未分類を含めて母数と一致させる。複数Labelの周辺合計と重複部分を区別し、重複Labelを排他的な円グラフ等へ載せない。
- 比較構造は「全問のうち」と「最適化を求める問のうち」の両方を必要に応じて示す。分母を省略して一方を他方のように説明しない。
- 全体だけでなく、資料／セット別、解答形式×判断根拠、主Domain×判断根拠等、偏りを発見できる少数の組合せを調べる。全組合せの表を無目的に増やさない。
- 少数例、不明例、分類者が迷った境界を結果と併記する。分類を変更したら影響する集計も更新する。元の観察を制作目標に合うように付け替えない。

例: 架空の一意な完全問30問を本文から分類した結果、成立案の優劣を求める意図が12問あり、そのうち比較成立8問・条件不足3問・完全案が一つの問1問なら、意図は12/30＝40%、確認済み比較は8/30＝26.7%、最適化意図の内訳としては8/12＝66.7%。これを「比較問題が40%確認できた」とは報告しない。この数字は計算例であり、制作の既定比率ではない。

## 6. 分析から問題を作り、その後で講義を設計する

制作へ進むときは、次の対応を追える状態にする。限定修正では変更に関係する範囲だけ扱う。

| Source観察 | 制作上の判断 | 生成後の確認 |
|---|---|---|
| 分類の定義、件数／母数、代表例、例外、根拠の強さ | 採用する形式・判断・比較構造、通常問題と各Mockの目標件数、採用理由 | 最終本文の再分類と実件数、目標との差、その理由 |

公式Domain重み・許可形式・ユーザー指定を優先し、その中でSourceの判断Patternと割合を教材の設計値へ反映する。小さな標本を公式出題率と断定せず、観察値と採用値を分ける。整数への丸め方と調整理由を残し、各Mockが独立して主要な判断を練習できるようにする。Sourceに一例あるという理由で全問へ展開したり、Source未観察の公式Objectiveを除外したりしない。

Sourceで技術的に未成立でも「最適化を問う意図」は制作に活用できる。ただし、新作では必要な条件と本当に成立する代替案を整え、その採用が観察済みの比較構造の単純再現ではないことを記録する。未観察Objectiveへの展開も、一次情報と観察Patternからの外挿として扱う。

少数の異なる問題を完成させて校正してから展開する。完成後は、作者のLabelや配分表だけでなくStem・全候補・解説から実際の判断を再確認し、型の偏り・実質重複・消えた比較を検出する。製品名や数値だけを替えた同じ決定を別の学習機会と数えない。

全面再作成は **Source分析 → 問題と解説の設計・作成 → 必要知識の抽出 → 講義・前提教材の設計 → Linkと表示を含む最終確認** の順で進める。講義へは正答Serviceだけでなく、近接候補の違い、比較が逆転する条件、必要なAPI・Data・障害の読み方まで接続する。分析資料を作っただけで制作依頼を完了としない。
